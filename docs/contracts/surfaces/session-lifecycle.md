# Session and harness process lifecycle

## Boundary and ownership

The service owns harness processes through `HarnessAdapter` and `ProcessProvider` ports. Pi's v1 lifecycle remains as specified below. The v2 Claude lifecycle uses the durable manager and adapter checkpoint.

The default `main.ts` composition remains the v1 service and does not activate durable-runtime HTTP routes. An embedding caller may inject an already prepared durable runtime into the existing API server for health/harness discovery and the basic four-route session cycle when a manager is present. Discovery-only injection profiles remain valid. The server neither creates nor owns that runtime, acquires its store/owner lock, starts providers, nor shuts it down. Readiness is fenced by current store ownership and synchronous closing state; it does not assert full v2 lifecycle readiness.

Terminal runtime shutdown closes the existing manager's create/resume admission synchronously. In-flight preflight, lock waits, execution-method capture, and native-result publication are fenced so closure cannot admit a late row/launch or publish a new `running` state. Work admitted before closure remains tracked for drain/unconfirmed shutdown reporting. Stop and physical cleanup remain available; failed cleanup is retained rather than represented as stopped.

## Claude lifecycle (API v2)

The `claude-code` adapter (alias `claude`) starts Claude CLI in stream-json print mode with replayed user messages enabled and a daemon-generated UUID passed as `--session-id`. It sends only a private correlated `initialize` control request; a valid correlated success response establishes readiness. No prompt, model turn, or synthetic initialization event is sent. Any startup or lifetime metadata declaring `session_id` must match the exact UUID; a `system/init` record is not required before the initialize acknowledgement. Resume requires the exact `claude.session` v1 checkpoint and starts `--resume <UUID>` without fallback; absence of a saved transcript fails explicitly. Stop is bounded and succeeds only after child exit is confirmed. The adapter advertises launch, resume, stop, and text-only `input.submit`; no empty transcript resumability guarantee is made.

## Observable flow

Claude text submit writes one exact native stream-json user message. The daemon input ID is local and is never translated to a native UUID. One active input is correlated by exact-content root user replay with `isReplay:true`, user role, and matching native session ID; nested tool/subagent records cannot acknowledge it. Acceptance requires that replay and successful write completion. Only the subsequent matching root result settles the input: success completes; terminal error fails without inventing a reason or exposing a cause. Write/ACK timeout or ambiguity is uncertain and never retried. CLI ordering and one-active-input behavior are the correlation assumption; optional native UUID echo is not required. Images and cancellation remain unsupported, with unsupported native control requests failing closed rather than approving/forwarding them. Stop closes input admission synchronously; child exit confirmation remains separate.

Create requires an absolute existing directory, inserts a `starting` session, starts Pi, obtains `nativeSessionId` from correlated successful `get_state`, and then reports `running`. Startup failure is safe and leaves `failed` with `{code,at}`. Stop performs bounded SIGTERM then SIGKILL cleanup and reports `stopped`; an accepted input interrupted by stop emits `input.state:uncertain`. Resume is allowed only for a stopped session with the exact saved native ID; startup failure reports `failed`. Unexpected child exit updates lifecycle status.

Pi v2 text/image submit permits one active input per session and sends one RPC `prompt` with exact text, `streamingBehavior:"steer"`, and optional canonical image blocks `{type:"image",mimeType,data}`. Decoded image data totals at most 20 MiB. The daemon's opaque input ID remains local and is never translated into a Pi ID. A correlated successful response is accepted; correlated rejection is definite failure. Timeout/write ambiguity is uncertain; the service never retries. A live `agent_settled` settles the sole current input, including uncertain delivery; terminal/dead streams cannot settle it. Stop or stream failure fences further writes and leaves unresolved delivery uncertain. Exact/current cancellation sends one correlated `{id,type:"abort"}` with no daemon input ID on the wire. Abort acknowledgement alone is not settlement: only a matching live `agent_settled` after an accepted abort marks failed/canceled; a successful abort ACK forbids repeat abort writes until that input ends. If settlement is already observed before cancel entry, cancellation rejects without a write and preserves normal completion. Definite abort rejection retains accepted/current input for explicit retry, and ambiguous delivery is uncertain without replay. v1 behavior remains unchanged.

Resume preserves the native ID and cwd; IDs are never inferred from local data. Pi JSONL accepts LF/CRLF and records are capped at 1 MiB. The owned running Pi execution supports read-only live status via correlated `get_state` and `get_session_stats` requests on its existing RPC reader; stop/shutdown intent, source-generation replacement, child/link death, and native-session mismatch fence the result before exposure. Only validated model/provider/id/name, effort, and usage fields are projected. Pi also supports read-only model catalogs through correlated `get_available_models` on this reader, projecting exact provider/id/name values with the existing missing-name fallback, preserving order and empty lists, and stripping unrelated native fields. It supports read-only effort catalogs through correlated `get_available_thinking_levels` on this reader, preserving exact level strings/order and empty lists; `current` is omitted because the RPC does not report it. Standalone `effort.change` first reads a fresh catalog and `get_state`, verifies the saved native session ID and exact level, writes at most one `{id,type:"set_thinking_level",level}` request without `persist:true`, and reads state again. A setter ACK alone is insufficient; it reports success only when readback confirms the same native session ID and exact requested thinking level. Clamp, mismatch, and any error after setter write remain unknown and are never retried. A pending effort change creates no lifecycle intent, so read-only queries remain available while its execution is current; actual stop/shutdown and source invalidation still fence the write and result. Final-write owner/source/deadline fences share the existing RPC link and do not disturb active input on pre-write refusal. It supports read-only command inventory through correlated `get_commands`, preserving eligible extension-command order and exact names/descriptions, mapping absent descriptions to empty strings, and dropping native metadata. Only `source === "extension"` commands with names matching `^[a-z][a-z0-9_-]{0,31}$` except `reload` are included. Catalog results are fenced against stop/shutdown, source replacement, child/link death, and stale ownership; the queries do not resume, retry, or mutate lifecycle state. RPC requests are `{id,type,...}`; correlated replies must be `{type:"response",id,command,success,data?}` with matching ID/command and boolean `success`. Readiness is `{id,type:"get_state"}` and requires `data.sessionId`. Submit is `{id,type:"prompt",message,streamingBehavior:"steer",images?:[{type:"image",data,mimeType}]}`; cancellation is correlated `{id,type:"abort"}`. Malformed/oversized records fail safely without exposing raw record text.

Pi v1 `message_update` with `assistantMessageEvent.type:"text_delta"` maps to `assistant.delta`; v1 `message_end` assistant and `agent_settled` map to message/turn completion. Durable Pi v2 text input consumes `agent_settled` only for settlement and does not forward rich output/activity events. `thinking_start/end` maps only to activity state, never reasoning text. `tool_execution_start/end` maps tool ID/name/error status without raw args/results in v1. `agent_start/end/settled`, `compaction_start/end`, and `extension_ui_request` `notify` map to activity/notification events in v1.

## Failure, recovery, and retention

The service keeps state only in memory. Restart recovery, durable history, and event replay are not guaranteed. Graceful shutdown stops all children with bounded escalation. Uncertain delivery remains explicit; no prompt is re-sent. Process output/stderr and prompt bodies are not logged.

## Non-goals and related contracts

No Claude image input, cancellation, output forwarding, model/options/control/commands, tool execution/approval, file-send, or callback broker; service restart process recovery, TLS, auth, and client migration are also excluded. See [API v1](api-v1.md), [adapter checkpoints](harness-adapters.md), and the harnessd Pi RPC compatibility source/test (`harnessd/src/harness/pi-rpc-harness.ts`, `harnessd/test/pi-rpc-harness.test.ts`).
