# Generic control plane

## Boundary and ownership

Core owns generic session lifecycle, persistence, registry, and capability routing only. Harness implementations are injected via registry; Pi and Claude are composition-root choices, never core cases. A new harness requires no core, API route, database column, or closed DTO-union change. See [adapter contracts](harness-adapters.md) and the [generic input runtime foundation](input-runtime.md).

## Generic identity and descriptors

`Session={id,harnessId,cwd,status,name?,nativeSessionId?,adapterOptions?,failureReason?,failedAt?}`; status is `starting|running|stopped|failed|uncertain`. IDs are authoritative opaque exact case-sensitive strings with existing grammar `[A-Za-z0-9][A-Za-z0-9._-]{0,127}`. Native session ID is optional opaque metadata, not universal routing identity or resume prerequisite. Harness IDs/aliases are registry-owned. Instance ID changes each daemon boot; connection/binding/callback/request/context IDs are separate non-credential namespaces.

Registry descriptor: `{id,aliases:string[],capabilities:string[],metadata?:Record<string,string>,options?:OptionDescriptor[],extensions?:ExtensionDescriptor[]}`. Option descriptor is `{key,label,values,allowCustom?,defaultValue?,dangerousValues?}`. Registry states each adapter's true capability subset; no synthetic parity (for example, no Pi-only feature implied for Claude).

## Standard capabilities

Generic ports cover launch/stop/resume, submit/images/current cancellation, live status/usage, models/effort, options, command inventory/execution, reload, and optional file-send/permission callbacks. DTOs: `Model={provider,id,name}`; `EffortCatalog={levels:string[],current?:string}`; `Usage={totalTokens?,inputTokens?,outputTokens?,cacheReadTokens?,cacheWriteTokens?,costUsd?,contextTokens?:number|null,contextWindow?,contextPercent?:number|null}`; `LiveStatus={model?,effort?,usage?}`; `Status={session,live?}`; catalogs expose descriptors and optional current/default/override/effective data; model changes can report model success with effort unconfirmed. Commands use `{name,description}` and result `handled|accepted` plus optional output. Input failures distinguish prompt rejected, hold timeout, held-and-stopped, and canceled. Unsupported capability fails explicitly. The durable manager's read-only live-status query requires both `status.read` and `usage.read`, a currently owned running execution, and an optional typed execution port; it never resumes or mutates session state. It records stop/shutdown intent at request entry before lifecycle-lock waiting and rechecks owner, execution, source generation, liveness, and pending state after adapter-port/method capture immediately before dispatch and after await. It does not hold the lifecycle lock during the query. The returned `LiveStatus` is a fresh plain snapshot containing only validated model, effort, and usage primitives. A model-catalog query similarly requires `models.read` and a typed execution port, with the same ownership/lifecycle fences and fresh validated `ModelCatalog` snapshot. Effort catalogs use the same fenced query path with `effort.read` and an optional typed execution port; Pi alone supplies available levels through its correlated read-only RPC, without inferring `current`. Standalone `effort.change` uses an optional typed execution port for an exact string on a currently owned running session; it does not resume, depend on `effort.read`, or couple to model changes. Its internal call context fences owner, source generation, liveness, stop/shutdown intent, and a 30-second operation lifetime before reads and at the final setter-write boundary. Results expose only `applied`; safe failures carry `not-applied` before possible mutation or `unknown` after it, with no automatic retry. The manager accepts arbitrary exact strings without normalization or a new length limit. Command catalogs use the same fenced query path with `commands.read` and an optional typed execution port; the standard DTO is `{commands:[{name,description}]}` with exact string fields and strict unknown-field rejection. Pi alone queries its correlated native inventory, projecting only extension commands with eligible native names and preserving order; missing eligible descriptions become empty strings. Generic adapters may use arbitrary command names. No catalog metadata is inferred.

Core carries no harness implementation, protocol code, model list, permission-mode enum, fixed option/value cases, closures, AbortSignals, or process handles. Namespaced operations/events/checkpoints follow [adapter schemas](harness-adapters.md); persisted generic fields and restart behavior follow [persistence](persistence.md).

## Lifecycle and uncertainty

Daemon owns processes and durable sessions. Startup never launches/resumes/replays from stored records; restart reconciliation and shutdown are specified in [persistence](persistence.md). Exact resume uses adapter checkpoint and identity protections where declared. Running clears failure metadata; starting/stopped may retain it. Input uncertainty is explicit and never automatically retried. Current cancellation targets exact active input; control cancellation is distinct.

Clients detach on bridge disconnect/shutdown: callback leases and selection guards expire, but daemon session/process remains alive. A missing lease fails callback closed. Loopback binding is not authentication. See [HTTP v2](api-v2.md) and [duplex bridge](bridge-v2.md).
